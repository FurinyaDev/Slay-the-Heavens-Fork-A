# 版本治理

为每个版本保留一个 Backlog 主任务及一份正式版本规划。Backlog 保存任务状态、依赖和交付记录。规划引用任务，呈现玩家范围、发版门禁、有效设计及同候选验收。GitHub PR、CI、产物归档与官方回执保存各自的原始证据。

- **Scope** 记录玩家实际得到的产品价值。通常列 3～5 个核心交付目标，版本主任务通常有 8 个或更少的直接子任务。超出时保留完整关系并记录范围评审的日期、决定人和理由。
- **Release Gate** 记录必须验收的质量成果。发版依赖具体可验证的成果，例如完整 CI 运行和同源产物审计，以及专门负责门禁的任务。
- **Engineering** 独立推进自动 CD、通用 CI 和治理能力。以原有工程任务保留接续和历史，版本规划引用所需成果及其验证入口。

每项交付保留需求或决策、有效设计及版本、Backlog Task ID、实现或继任 PR 和验收证据。沿用原 ID。延期保留源 PR 或原始证据的固定位置、接续任务和目标版本。缺少需求、设计或实现时，在规划标为待补并在准入时复核。

| 状态 | 证据 |
| --- | --- |
| 已开发 | 来源分支或精确提交、定向验证。 |
| 已合入 | 实际目标分支及合入提交。 |
| 已验收 | 对应正式源码和产物的原始验收证据及独立 Review。 |
| 已发布 | 上线确认、实际平台版本、可核验发布凭证和归档。 |

## 产品行为与启用

产品 PR 写明玩家实际能观察到的变化、Backlog 编号、目标版本与固定批准来源。设计批准复用现有[参考索引](../design/UI_REFERENCES.md)的相同版本、标签和状态。已有必要修复可引用对应批准范围和回放。新增行为需要可追溯的 Owner 决定。独立审查从实际差异逐条核对批准，并反向检查批准的范围是否被如实实现。任务标签、阶段备注、测试结果分别提供归属和验证信息。

v2.2.0 期间，`develop` PR 的实际生产、打包配置或工作流差异进入既有 Quality 历史检查，沿用原生独立 AI Review。PR 写 `Product-Scope: v2.2.0 | TASK-编号 | 批准条款原文 | 固定批准来源`，每项行为一行，配合正文说明实际行为。经独立复核只有内部工程变化的 PR 使用 `Product-Scope: v2.2.0 | none`。签署原有独立评审 JSON 时增加 `productScope: { "version": "v2.2.0", "declarationSha256": "<精确各行以 LF 连接的 SHA-256>" }`。将现有原生评审 ID 填入 `Product-Review`，沿用当前 HEAD/BASE/合并树。可先复用 Fork 定向验证与独审，再重跑主仓 Quality 读取完整回执。

先在实验目录或 Fork 隔离未获准的研究。确需提前集成且已有授权时，沿用既有构建配置默认关闭，在关闭路径验证没有模块加载、分配、订阅或可达入口，保留配置、构建读回与独审回执。正式启用由目标版本的批准决定和正式配置共同确定。普通已批准修复直接进入其原有运行路径。明确否决的行为删除。

## Release 准入

核对版本规划、Backlog 及选定源码范围。确认必要 PR 已进入 develop，生产分支的修复和 Git 祖先关系均已继承，保留对应 CI 与独立审查。按现有分支流程从经核对的 develop 提交建立 Release，冻结范围。冻结后仅接必要缺陷修复。新增需求进入后续版本。例外应记录批准者、日期、理由、影响范围及重新验收的门禁。

## 正式上线

为冻结源码完成全部必要 Full 分片，构建并审计正式有声 GIL，将源码、配置、产物 SHA-256、归档和可复现构建收据绑定同一候选。保留事故防回退、六档受限算力、压力、超载与恢复、性能、容量、稳定性、美术、Simulator、PC、实体手机和官方平台证据。阈值以既有合同或实测基线为依据。独立评审和 Owner 确认后执行正式发布。[发布操作单](../PUBLISHING.md)

## 发布后结项

核对正式平台回执、实际平台版本、工程 Tag 和最终归档。每次 Release 或 Hotfix 合入 master 后，完整回流 develop，核对生产提交是 develop 祖先，并逐项验证实际修复继承及合后 CI。通过后关闭版本主任务。[分支收口](../BRANCH_LIFECYCLE.md)
